## Artifact contract for both runs

Use the supplied HTML renderer, not a new web application. Read skills/project-team/references/reporting.md.

Each run returns one bundle:
- report.html: a standalone executive review, with overview, actual vs planned outcomes, Kanban, relative Gantt, team roles/identities, acceptance, deputy decisions, risks, standups and evidence.
- report-data.json: the same report's structured snapshot, referencing canonical work-item IDs. If no board exists it can be the pilot's one work-item source, not an extra registry.
- review.md: a concise product verdict and workflow verdict, evidence links, consumption and next recommendation.
- handoff.md: a compact complete-scope reference, current candidate, owners, remaining items, unresolved decisions and next action.
- evidence/: real screenshots/clips and references to retained test/save/build artifacts. Avoid copying large existing evidence unnecessarily.
- launch instructions and the actual runnable candidate path, with relevant preserved branch saves.

At kickoff the dashboard must say Not run/Unverified, not imply success. Update only at meaningful milestones and final closure. Unknown usage, dates or agent identities remain unknown. Never invent a percentage complete or claim the file monitors agents live.

The prepared dashboard in pilots/life-explosion-delivery-review.html is an example with real task proposals and no fabricated results. The JSON beside it supplies the exact template shape. A future run replaces planned values with observed ones and retains forecasts distinctly. Actual media uses relative paths within the bundle where possible.

## How we will review the results when you return

Bring the run's final task link plus report.html, report-data.json, review.md and handoff.md. If only the local folder exists, provide its absolute path. Do not paste the full operational transcript.

We will inspect five things:
1. Product: compare each acceptance row with the runnable result and its evidence. Source, tests, prepared drivers and ordinary controls are different evidence classes.
2. Preservation: confirm original checkpoints, inherited investment and unrelated work were preserved.
3. Execution: check elapsed time and available usage, repeated attempts/builds, time spent reporting, and whether PM execution duties expanded.
4. Team judgment: inspect deputy recommendations, evidence, PM disposition and whether a challenge improved a decision. Agreeing with a sound plan is valid.
5. Continuity: attempt fresh-context reconstruction from the compact handoff, original authority references and live state. Missing capacity/time means not assessed, not pass.

Return separate product and workflow verdicts: pass, needs revision, or inconclusive. A useful partial result can coexist with a failed workflow or incomplete acceptance. A pretty dashboard cannot compensate for missing gameplay.

Launch the larger challenge only after reviewing Trial1 and fixing material workflow or licensing/access issues. After Trial2, decide whether to adopt the skill, narrow it or reject this version. More team activity by itself is not a success metric.
