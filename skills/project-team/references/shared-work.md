# Shared project records and ceremonies

Use the project's existing tools. A local Markdown work table is sufficient for a pilot if no board is established. If a connected board is already configured, reuse its IDs and authorization. Do not provision an external service or duplicate the board just to follow this skill.

## One project brief

Keep the approved outcome and all selected requirement groups, source references, exclusions, decision authority, current delivery boundary and canonical artifact/board location. Link to full approvals instead of pasting them into every assignment.

## Work-item fields

Each actionable item contains:
- stable ID, player/user-visible outcome and authoritative requirement reference;
- owner role and actual agent identity, dependencies and current status;
- exact source/workspace baseline, exclusive write scope and shared-resource reservation;
- acceptance result required and proportionate verification;
- estimate range, agreed resource/review boundary and assumptions where relevant;
- current blocker or next action;
- implementation, review and evidence links, with actual author/reviewer identities.

PM owns priorities, scope and assignments. Members update their assigned items; conflicting shared edits go through the PM or supported board concurrency controls. QA records observed results, and the deputy records its verdict. The board records work; it does not grant authorization.

Suggested Kanban: Ready, In progress, Review, Blocked, Done. Keep one active implementation item per executing member unless a real wait permits independent work. Blocked items name a dependency and a next check. Done means the item's acceptance is met, not the entire project is complete.

## Timeline / Gantt view

Build the timeline from the same item IDs, dependencies, available capacity and estimate ranges. Mark the critical dependency chain and distinguish forecast from commitment. Where evidence cannot support dates, show ordered batches and dependencies first. Update the view when the dependency or forecast changes, not after every tool call.

## Standup and review records

Each participating member contributes: completed change or finding, next action, blocker/help needed. A standup can be one batched message exchange; do not simulate dialogue between absent agents or claim participation that did not happen.

A design review records the decision and its reason. A demo links the actual runnable behavior or inspected output. QA records acceptance separately from implementation. A deputy review records verdict, evidence, proposed alternative, PM disposition and unresolved owner decision, if any.

At a retrospective retain only a demonstrated problem, the change to the next batch and who owns it. Avoid transcripts of meetings that introduce no decision.

## Current manager briefing

Keep current:
1. Complete delivery objective and authority references.
2. Candidate/workspace identity and known verified behavior.
3. Remaining requirement groups and critical dependencies.
4. Active people, work items and exclusive resource owners.
5. Current decisions, material objections, blockers and next assignments.
6. Resource boundary, observed consumption, enforcement limitations and last review.

Replace obsolete current statements; preserve durable decisions or evidence in their existing history locations. Do not append every build manifest or entire completed task report to this briefing.

A successor should be able to explain what is being delivered, why the next work matters, what it may change, what remains uncertain and who can write/run what. If it cannot, repair the missing information before dispatch. This is a practical handoff check, not a second reporting system.
