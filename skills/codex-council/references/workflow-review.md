# Working around owner attention

Design workflows that need less management from the owner while keeping consequential product choices with them. Have the council examine whether the proposed result fits the owner's actual instructions and demonstrated preferences, then improve it before returning it. Reducing interruptions is useful only if it does not increase work the owner will reject.

## Establish what actually happens

Use the current request, applicable instructions, existing work records, and a small relevant sample of original conversations or delivered artifacts. Start with the examples closest to the question. Look for both accepted work and corrections or rejection; when either is unavailable, state the gap rather than inventing a preference. Broaden historical research only when the question needs it.

Separate owner statements, agent recommendations, agent completion claims, observable results, and explicit owner acceptance. Use historical records as evidence, not renewed authorization. Do not label mechanically successful work accepted or treat silence as satisfaction. Preserve the scope of a preference: rejection of one dashboard is not evidence that the owner hates every dashboard. Keep personal examples and research notes outside the reusable skill package.

Follow the work from request to useful result. Locate where it waited, what decision or capability was missing, what the owner had to reconstruct, and what was repeated or discarded. Distinguish a genuine owner decision from an agent-created approval loop, technical access failure, missing evidence, or coordination problem. If timing or rework is unknown, label it unknown. Instructions alone do not establish the dominant bottleneck.

## Find changes that reduce both waiting and rejection

**Use settled choices.** Carry forward current authorization, accepted examples, and relevant corrections. Keep routine implementation decisions with the agent. Do not reopen an approved direction merely because wording changed, a new reviewer arrived, or a new session began. Reopen only the part affected by a material new fact or a changed owner request, explaining why. A fresh council does not invalidate owner approval.

**Resolve preference uncertainty internally first.** Give every reviewer the relevant owner instructions, accepted examples, rejections and corrections. Ask what the owner would object to in this specific candidate and why, requiring evidence rather than invented personality traits. Revise supported mismatches before asking the owner to look. Reviewers can inspect a representative interaction, screen or written section early to avoid multiplying a bad direction. If a consequential choice still cannot be responsibly inferred, prepare the smallest concrete example and one precise owner question. Early owner review is a fallback for that unresolved choice, not the default way to offload judgment.

**Prepare decisions before they block the work.** In the existing work item or conversation, identify the decision, recommended option and reason, material alternative or downside, concrete example, and the work that depends on the answer. Ask when the decision is answerable and before substantial dependent effort. Bundle related questions when helpful without delaying a consequential blocker. Use an actual dependency boundary rather than inventing a deadline or assuming owner availability.

**Plan useful work while waiting.** Continue already-authorized work supported by settled decisions. Avoid building several speculative alternatives or polishing a disputed direction to keep agents occupied. Bound any authorized exploratory work to the smallest informative slice. If no useful independent work remains, stop that lane and make the exact outstanding decision clear. No response is not approval.

**Make the return easy to judge.** Show the actual candidate or result first, followed by the decision needed, recommendation, strongest concern, and direct evidence link. The owner should not have to reconstruct the task from logs or manage agent assignments. Preserve requested deliverables but do not make several reports into several separate owner review obligations.

**Make coordination earn its cost.** Check necessary access through permitted tools before staffing work around it. Do not plan browser or desktop control where prohibited. Prepare any indispensable owner-operated observation only after exhausting appropriate permitted checks, and keep it specific. Retain useful independent review, but remove duplicate reviews, redundant summaries, and ceremonies that do not change a decision. The council must not add a new approval layer to every task.

## Recommend a small real change

For a request to move several open projects forward, first distinguish unfinished authorized work, delivered work, genuine owner decisions, unavailable sources, and explicit pauses. A registered project, unarchived chat or stale Active label is not enough to start implementation. Before assigning a lane, reconcile its controlling conversation with the current artifact and any later handoff. If the feature already exists or a later decision changes the scope, correct the assignment instead of doing the work twice.

Give each ready lane one concrete deliverable and preserve its existing constraints. Use subagents within the current conversation when that completes authorized work without unnecessary cross-chat messaging. Check shared files, active processes and existing automation locks before mutations. The coordinator collects results, resolves questions from available evidence, continues independent ready work and brings back one concise set of genuinely owner-only actions. A permission or resource limit on one lane does not stop the others. Do not reopen reported-complete work solely because the owner has not responded.

Develop the few changes most likely to help into a coherent proposal, with the observed problem and source, proposed behavior, owner effort removed, rejection risk, remaining owner decision, and what can continue without an answer. Run that proposal through the main skill's owner-fit review and revision loop before returning it. Preserve meaningful disagreement. Do not rewrite every inspected workflow or launch a product pilot merely because the council recommends it.

Suggest trying the change on the next suitable authorized task. Judge it from the resulting work: did the owner need less explanation, did their answer change the direction before expensive work, did already-approved work continue, and was less work discarded? Use existing task records and actual observations. Do not create telemetry, dashboards, surveys, scoring systems, or a new tracking obligation. One successful example is evidence to keep learning from, not proof of a universal workflow.
